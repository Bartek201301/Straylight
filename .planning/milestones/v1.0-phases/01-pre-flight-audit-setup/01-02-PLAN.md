  <name>Task 1: Audit environment variables and document security posture</name>
  <files>.planning/phases/01-pre-flight-audit-setup/01-env-audit.md</files>
  <action>
1. Verify .env files are gitignored:
   ```bash
   grep -n "\.env" .gitignore
   ```
   Confirm patterns like `.env`, `.env.local`, `.env*.local` are present.

2. Check that no .env files are tracked by git:

   ```bash
   git ls-files | grep -i "\.env"
   ```

   Should return empty.

3. Search for hardcoded secrets in source code:

   ```bash
   grep -r "sk_\|api_key\|secret\|password\|token" src/ --include="*.ts" --include="*.tsx" -l
   ```

   Examine any matches to confirm they are references to `process.env.*` and not actual secret values.

4. Verify server-only secrets are not used in client components:
   - `SUPABASE_SERVICE_ROLE_KEY` — should only appear in files that run server-side (API routes, lib modules imported only by API routes)
   - `AI_API_KEY` — should only appear in API routes
   - `MAILCHIMP_API_KEY` — should only appear in server-side mailchimp module
   - Search for these variable names and verify each usage file is server-side only.

5. Check for `NEXT_PUBLIC_` prefix correctness:
   - Variables with `NEXT_PUBLIC_` prefix are exposed to client — verify they contain no secrets
   - Variables without the prefix should not be accessed in client components

6. Create `.planning/phases/01-pre-flight-audit-setup/01-env-audit.md` with:
   - Table of all environment variables: name, type (public/secret/config), location, server-only status
   - Security findings summary (should confirm: no issues found, matching research findings)
   - List of referenced-but-optional variables (affiliate IDs, REDIS_URL, debug toggles)
   - Recommendation: Note that no runtime env validation exists (Zod schema) — recommend for future phase
   - Overall status: PASS or FAIL with details

The research already found all of this to be clean. This task is verification — confirming the research findings are accurate by running the actual checks.
